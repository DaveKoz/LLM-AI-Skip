# SkipFuse UI Cross-Platform Architecture Updates

## How to Make Android Work Like iOS

This document synthesizes the incompatibilities discovered while making a SkipFuse app work correctly on Android. It is a practical guide for SkipFuse UI development — not just a list of banned APIs, but an explanation of *why* things break and *how* to write code that behaves identically on both platforms.

---

## 1. The Core Architectural Difference

### iOS: `withObservationTracking` Tracks Everywhere

On iOS, SwiftUI's `@Observable` macro uses `withObservationTracking` to monitor property reads across the entire view tree. If a parent owns `@State var vm = ViewModel()` and a child view reads `vm.isLoading`, iOS automatically subscribes that child to any future change of `isLoading`. When the async load completes and `isLoading = false`, every child that ever read it re-renders automatically.

### Android: Compose Does NOT Replicate Cross-View Observation

Skip's Compose bridge does NOT implement this. When a child view receives `vm` as a plain `var` parameter, changing `vm.isLoading` on the Kotlin side updates the backing object but **never invalidates the Compose snapshot** for that child composable. The child view stays frozen at whatever state it had during its very first composition.

### What This Means in Practice

| Pattern | iOS | Android |
|---------|-----|---------|
| `@State var vm = ViewModel()` passed to child as `var vm: ViewModel` | Child re-renders when `vm` props change | Child frozen at initial state |
| `@State var flag: Bool` passed to child as `var flag: Bool` | Child re-renders when `flag` changes | Child re-renders when `flag` changes |
| `vm.items` read directly in child `body` | Updates when items load | Shows empty / stale forever |

**Takeaway:** On Android, `@Observable` works *within* a single view's `body`, but NOT across view boundaries. Primitive `@State` values DO work across boundaries because Skip generates explicit `remember { mutableStateOf(...) }` calls for them.

## 2. The `@Observable` Cross-View Freeze (Rule #73)

### Problem

Child views that receive an `@Observable` object as a plain `var` parameter never re-render when that object's properties change after an async load.

### Example

In your app, `ContentView` loaded data and set `vm.isOnTeam = true`. The `TeamHubView` child still showed "not on a team yet" because it was composed with the initial `false` value and never updated.

### Root Cause

Skip generates something like this for the child composable:

```kotlin
// Kotlin generated by Skip for TeamHubView(vm: vm)
@Composable
fun TeamHubView(vm: MyViewModel) {
    // vm.isOnTeam is read ONCE during first composition
    // No Compose subscription is created for vm property changes
    if (vm.isOnTeam) { ... } else { "Not on a team" }
}
```

### The Fix: Shadow State as `@State` Primitives

```swift
struct ContentView: View {
    @State var vm = MyViewModel()
    @State var isOnTeam: Bool = false        // <- THIS triggers recomposition
    @State var orgId: String = ""
    @State var isDataLoading: Bool = true

    var body: some View {
        if isDataLoading {
            ProgressView("Loading…")
                .task {
                    await vm.loadData()
                    // Copy from ViewModel to @State — THIS triggers recomposition
                    isOnTeam = vm.isOnTeam
                    orgId = vm.teamOrgId ?? ""
                    isDataLoading = false
                }
        } else {
            TabView {
                // Pass PRIMITIVES, not the ViewModel, to children
                TeamHubView(isOnTeam: isOnTeam)
                ScheduleView(orgId: orgId)
            }
        }
    }
}

struct TeamHubView: View {
    var isOnTeam: Bool  // primitive param — change forces recomposition
    var body: some View {
        if isOnTeam { TeamContent() } else { EmptyState() }
    }
}
```

### Why This Works

When Skip transpiles `@State var isOnTeam: Bool`, it generates:

```kotlin
val isOnTeam = remember { mutableStateOf(false) }
```

Changing `isOnTeam = true` from the parent invalidates the parent's composable. The parent re-composes, creating a NEW `TeamHubView(isOnTeam: true)` with an updated parameter. The child composable receives a new value and re-renders.

### When to Apply This Pattern

Apply whenever a child view's `body` branches on state that changes after an async operation:
- Loading spinners (`vm.isLoading`)
- Empty states (`vm.items.isEmpty`)
- Conditional content (`vm.isOnTeam`, `vm.isAdmin`)
- Derived display values (`vm.teamOrgId`)

**Do NOT apply to:** Internal view state, form fields, or properties that don't gate the `body` structure.

## 3. `List` + `Section` + Nested `ForEach` Items Invisible (Rule #74)

### Problem

Skip maps SwiftUI `List` to Jetpack Compose `LazyColumn`. When a `List` contains `Section` blocks that each contain a nested `ForEach`, the section **header** renders but the **items inside the `ForEach` never appear** on Android.

### Example

In the schedule view, "Category A" appeared as a header with zero rows underneath, even though `total=1 categoryA=1` was confirmed in the logs.

### Root Cause

`LazyColumn` has a flat item key namespace. `Section { ForEach(items) { ... } }` creates a nested content scope that Compose's `LazyColumn` item expansion does not properly flatten. The section composable is created, its header is rendered, but the `ForEach` items are silently dropped during the `LazyColumn` item-to-composable mapping.

### The Fix: Flat `ScrollView` + `VStack`

```swift
// ❌ WRONG — headers show, rows invisible on Android
List {
    ForEach(types, id: \.rawValue) { type in
        let items = scheduleItems.filter { $0.type == type }
        if !items.isEmpty {
            Section {
                ForEach(items) { item in
                    NavigationLink(destination: DetailView(item: item)) {
                        RowView(item: item)
                    }
                }
            } header: {
                Text(type.rawValue)
            }
        }
    }
}

// ✅ CORRECT — flat layout, works identically on both platforms
ScrollView {
    VStack(spacing: 0) {
        ForEach(types, id: \.rawValue) { type in
            let items = scheduleItems.filter { $0.type == type }
            if !items.isEmpty {
                // Manual header
                Text(type.rawValue)
                    .font(.subheadline.weight(.semibold))
                    .foregroundColor(type.color)
                    .frame(maxWidth: .infinity, alignment: .leading)
                    .padding(.horizontal, 16)
                    .padding(.vertical, 8)
                Divider()
                // Items as direct children of VStack
                ForEach(items, id: \.id) { item in
                    NavigationLink(destination: DetailView(item: item)) {
                        RowView(item: item)
                    }
                    Divider()
                }
            }
        }
    }
}
```

### Trade-offs

| Aspect | `List` + `Section` | `ScrollView` + `VStack` |
|--------|-------------------|------------------------|
| iOS rendering | Works perfectly | Works perfectly |
| Android rendering | Headers only, items missing | Works perfectly |
| Performance (large lists) | Lazy (items created on scroll) | Eager (all items created at once) |
| Pull-to-refresh | `.refreshable` works | `.refreshable` works |
| Row separators | Automatic | Manual `Divider()` |

For small-to-medium lists (< 50 items), `ScrollView` + `VStack` is the reliable cross-platform choice. For very large lists, consider paginating the data or using a platform-specific branch.

## 4. `Button(action: {})` Is Completely Untappable (Rule #75)

### Problem

A `Button` with an empty action closure renders visually but **never responds to taps** on either iOS or Android. This is particularly dangerous because the UI looks interactive during debugging.

### Example

During debugging, we temporarily replaced `NavigationLink` with `Button(action: {})` and couldn't understand why tapping the schedule row did nothing on either platform.

### Root Cause

The SwiftUI runtime optimizes away tap gestures for closures it can prove are no-ops. Skip's transpiler likely propagates this optimization to Compose, where the `clickable` modifier is not applied when the action closure is empty.

### The Fix: Never Ship Empty Actions

```swift
// ❌ WRONG — renders but never responds
Button(action: { /* TODO: implement */ }) {
    RowView(item: item)
}

// ✅ CORRECT — for push navigation
NavigationLink(destination: DetailView(item: item)) {
    RowView(item: item)
}

// ✅ CORRECT — for state-driven modals
Button(action: { selectedItem = item }) {
    RowView(item: item)
}
.sheet(item: $selectedItem) { item in
    DetailView(item: item)
}

// ✅ CORRECT — for non-interactive display rows
HStack {
    RowView(item: item)
}
```

### Related: NavigationLink on Android

`NavigationLink` works reliably on iOS inside a `NavigationStack`. On Android, it *usually* works if the parent has a `NavigationStack`, but test thoroughly. If `NavigationLink` fails on Android, use `@State var selectedItem` + `.sheet(item:)` or a custom navigation pattern with explicit state management.

## 5. `logger.debug()` Is Filtered on Android (Rule #72)

### Problem

`Logger.debug()` maps to Android `Log.d()`, which is **suppressed by default** on most devices and emulators. All diagnostic logs written with `logger.debug()` are silently swallowed.

### The Fix: Use `logger.info()` for Any Android-Visible Logging

```swift
// ❌ WRONG — invisible on Android
logger.debug("[trace] loaded \(items.count) items")

// ✅ CORRECT — visible on both platforms
logger.info("[trace] loaded \(items.count) items")
```

Additionally, Swift 6 strict concurrency requires capturing `self`-owned properties in local `let` constants before passing them to any logger call (the `OSLogMessage` autoclosure has `@autoclosure` semantics):

```swift
// ❌ WRONG — compile error: "reference to property 'items' in closure requires explicit 'self'"
logger.info("count=\(items.count)")

// ✅ CORRECT
let count = items.count
logger.info("count=\(count)")
```

**ADB command:** `adb logcat -s MyApp` (tag = `category:` value from `Logger(subsystem:category:)`)

## 6. Conditional `TabView` Tabs Break Compose Pager (Rule #70)

### Problem

Using `if condition { SomeView().tabItem{...}.tag(...) }` inside a `TabView` changes the tab count at runtime. iOS handles this via tag-based selection. Android/Compose uses an index-based pager — inserting a tab at position N shifts all subsequent indices, causing the wrong tab to be selected.

### The Fix: Fixed Tab Count with Internal Branching

```swift
// ❌ WRONG — tab count changes after data loads, pager jumps
TabView(selection: $tab) {
    ScheduleView().tabItem { ... }.tag(.schedule)
    if vm.isOnTeam {
        TeamView().tabItem { ... }.tag(.team)
    }
    MoreView().tabItem { ... }.tag(.more)
}

// ✅ CORRECT — always render all tabs, branch inside each tab's body
TabView(selection: $tab) {
    ScheduleView().tabItem { ... }.tag(.schedule)
    TeamView(vm: vm).tabItem { ... }.tag(.team)   // always present
    MoreView().tabItem { ... }.tag(.more)
}
```

## 7. `@AppStorage` for Tab Selection Persists Across Logins (Rule #71)

### Problem

Using `@AppStorage("selectedTab")` for tab selection in login-gated views persists the selected tab across logout/login cycles. If the user was on the "Team" tab, logs out, and a different user logs in, they'll land on "Team" even if they have no team access.

### The Fix: Use `@State` for Login-Gated Tab Selection

```swift
// ❌ WRONG — persists across sessions, wrong tab for different user
@AppStorage("selectedTab") var tab = ContentTab.schedule

// ✅ CORRECT — resets when ContentView is recreated after login
@State var tab = ContentTab.schedule
```

## 8. Firestore `.order(by:)` Excludes Documents on Android (Rule #69)

### Problem

Firestore `.order(by: "date")` on Android fetches from the server and **excludes any document missing that field**. iOS may return them from cache. This causes silent data loss.

### The Fix: Fetch Unordered, Sort in Swift

```swift
// ❌ WRONG — docs missing "date" are silently excluded on Android
let snap = try await db.collection("items")
    .order(by: "date", descending: false)
    .getDocuments()

// ✅ CORRECT — fetch all docs, sort in Swift
let snap = try await db.collection("items").getDocuments()
let items = snap.documents
    .map { parse($0) }
    .sorted { $0.date < $1.date }
```

## 9. Recommended SkipFuse UI Architecture Pattern

Based on all findings, here is the recommended pattern for data-driven views in SkipFuse:

```swift
struct ParentView: View {
    @State var vm = SomeViewModel()
    // Shadow ALL display state as @State primitives
    @State var items: [Item] = []
    @State var isLoading: Bool = true
    @State var errorMessage: String? = nil

    var body: some View {
        if isLoading {
            LoadingView()
                .task { await load() }
        } else {
            // Create child views ONLY after data is ready
            // Pass primitives, NOT the ViewModel, for anything that gates body
            ChildView(items: items, errorMessage: errorMessage)
        }
    }

    func load() async {
        await vm.load()
        // Copy from @Observable ViewModel to @State primitives
        items = vm.items
        isLoading = vm.isLoading
        errorMessage = vm.errorMessage
    }
}

struct ChildView: View {
    var items: [Item]          // primitive/array param — recomposition works
    var errorMessage: String?  // primitive param — recomposition works

    var body: some View {
        ScrollView {
            VStack(spacing: 0) {
                if let err = errorMessage {
                    Text(err).foregroundColor(.red)
                }
                ForEach(items, id: \.id) { item in
                    NavigationLink(destination: DetailView(item: item)) {
                        RowView(item: item)
                    }
                    Divider()
                }
            }
        }
    }
}
```

### Checklist for Every New View

- [ ] `@State` primitives for all display state that gates `body` branches
- [ ] Copy from `@Observable` ViewModel to `@State` after async load completes
- [ ] Pass primitives (not ViewModel) to child views for anything conditional
- [ ] Use `ScrollView` + `VStack` instead of `List` + `Section` + nested `ForEach`
- [ ] Use `NavigationLink` (never empty `Button`) for row tap handling
- [ ] Use `logger.info()` (never `logger.debug()`) for Android-visible diagnostics
- [ ] Capture `self`-owned properties in local `let` before logger interpolation
- [ ] Never conditionally add/remove `TabView` tabs — fixed count, branch inside body
- [ ] Never use `@AppStorage` for tab selection in login-gated views
- [ ] Never use `.order(by:)` in Firestore queries — fetch all, sort in Swift
